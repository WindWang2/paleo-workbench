# 04 — Ordering Engine (V11)

## 1. Effective order definition

```
effective order =
    System default (role band + science sub-order)
  + User override (persisted per-node order key)
  merged in one coordinate space (order keys)
  + Temporary overlay (session-scoped, never persisted)
```

Stage semantics do NOT participate in order (stage changes visibility/
lock/tool context only — union tree is shared, 03/§5).

## 2. Order keys (fractional string keys)

Every tree child (group or layer) carries `order_key: str`.

- Alphabet: `a..z` (26), midpoints between two keys always exist.
- Default keys: assigned at plan-build time from the node's **band rank**
  and **science sub-order** with a fixed stride: key = key_between
  interpolation of position — concretely, the default sequence for a
  container of n children is generated by the standard fractional-index
  stride (deterministic: same children → same keys).
- User drag: moving a node between neighbors A and B assigns
  `midpoint(A, B)` — **no neighbor renumbering, ever**.
- Rebalance: when a key grows pathological (> 64 chars, i.e. > ~100
  consecutive inserts at the same spot), the container's keys are
  re-strided in one diff transaction (rare, user-visible as one undoable
  reorder).
- Persistence: the key itself (in `state.tree`); migration assigns keys
  from positional order with fixed stride — deterministic, idempotent.

Why not integer ranks / floats: gaps exhaust (renumber storms at scale),
floats exhaust precision after ~50 midpoints. String keys have neither
failure mode and are lexicographically sortable everywhere (Python sort,
C++ std::string::operator<, JSON) with zero parsing.

existing band order already encodes the same science (cartographic on top,

## 4. Ordering computation (pure, O(N log N))

```
sort key(node) = (
    group band of parent        # groups ordered among themselves
    node.order_key              # persistent, default or override
    tiebreak: node id           # total determinism
)
```

- Groups: default keys re-derived from template band each build (system
  groups are fixed-band; factor groups ordered by task id; user groups by
  persisted keys). System group order keys are NEVER user-overridable.
- Layers: default key = band-derived; override key = persisted user drag.
  A layer dragged within its group keeps its override across syncs (the
  D3-ws discard bug is closed by construction: `build_desired_tree` no
  longer derives order from snapshot order).

## 5. Render/legend/layout order (one walk)

`layer_ids_top_first()` (depth-first, top-first) is THE single source:
- canvas: QGIS tree order (bridge `QgsLayerTreeMapCanvasBridge`) — matches
  by construction; parity test added.
- legend: same walk; explicit `filter_layers` override remains opt-in.
- layout: `layout_export` now walks the full tree including groups
  (grouped layers no longer dropped).
- fallback painter: consumes the same walk (top-first); the bottom-up
  snapshot-assembly convention is renamed and documented (`layers_bottom_up`
  = reversed walk) — one named convention, parity-tested.

Flat legacy mode (`set_mirror_layer_order`) remains for groupless stacks,
now typed as top-first explicitly.

## 6. Temporary overlay

`TemporaryOrderOverlay` (session-scoped): map layer_id → overlay key +
expiry (gesture end). Applied only at render-plan assembly; never written
to state; cleared on stage switch / session end. Use case: pull QC /
selection scratch layers to top during inspection.

## 7. Scale invariants (structural, test-enforced)

- midpoint insert: O(1) key computation, zero neighbor writes
- move one layer: diff emits exactly one move op → one bridge call
- move group: one op
- 1000-layer container sort: O(N log N), no `list.index` in any sort key
  (rank dicts precomputed — `known_ids.index` pattern banned by test)
- default tree build: same input → byte-identical snapshot (pinned)
