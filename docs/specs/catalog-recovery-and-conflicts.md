# 数据目录：中断恢复与冲突行为说明（用户指南）

适用版本：C++ 收口波次 01 线（catalog/project closure）起。
面向：日常使用工程与数据目录（分类 / 标签 / 溯源 / 工作副本）的用户。

## 1. 数据目录是什么，保存在哪里

打开或新建工程 `<名字>.paleo.json` 后，数据目录（catalog）负责记录工程里
所有受管数据资产：分类、版本、标签、溯源运行与工作副本登记。落盘位置：

- `<工程名>.artifacts/catalog.sqlite` —— 唯一权威库（SQLite，WAL 模式）；
- `<工程名>.artifacts/metadata/catalog.json` —— 人类可读检查点（含 `.bak` 备份）；
- `<工程名>.artifacts/raw|derived|.../` —— 受管载荷文件（按阶段/资产/版本编号存放）。

`.paleo.json` 与数据目录是两个独立文件：工程文件损坏走工程文件自己的恢复
决策表；数据目录损坏走本文第 3 节的恢复梯。

## 2. 正常流程：导入 → 工作副本 → 提交

1. **导入**：把文件导入工程时，系统复制（绝不引用）文件进入受管存储并
   计算内容指纹（sha256）。原文件后续修改不影响快照。
2. **工作副本**：对已有版本点"创建工作副本"会得到一份可编辑副本，系统
   登记其状态（checked_out → dirty → committing）。
3. **提交**：提交会生成一个新的不可变版本（原版本保持原样，作为溯源来源）。
4. **关闭工程**：关闭时写出目录检查点并释放数据库句柄；重新打开后一切
   状态一致（版本、标签、当前指针、修订号）。

## 3. 中断恢复（崩溃 / 断电 / 强杀之后）

重新打开工程时自动执行，无需手动操作：

- **提交中（committing）断掉**：提交采用两段式。若新版本已落库，登记行被
  直接清理；若还没落库，工作副本回到 dirty 状态，可重新提交——已完成的
  拷贝不会被丢弃，用户数据不会因恢复而丢失。
- **找不到载荷的工作副本**：该副本被丢弃并计入恢复报告（打开后可见）。
  受管原版本不受影响。
- **临时残留**（崩溃保存留下的 `.place-*` 临时文件、空目录）会被保守清扫；
  只有绝不可能被任何版本引用的文件才会被删除。载荷、工作副本、回收站
  不会被该清扫触碰。
- **恢复报告**：恢复结果（清理了几个已提交记录、几个副本回到 dirty、几个
  因载荷丢失被丢弃、保留了几个）以中文逐条呈现，也可从
  `CatalogRecoveryReport`（`closure_catalog_service.hpp`）读取。

## 4. 冲突行为（多开 / 多实例）

数据目录用**修订号（revision）+ 单写者**保护：

- 每次写入在事务内比对修订号基线。若另一实例在你打开期间已提交，你的
  写入会以 `conflict_base_version`（stale_write）被**明确拒绝**。
- 系统**绝不自动覆盖**他人提交；同样，检查点（manifest）导出也走同一
  门禁，被拒绝时会给出完整中文提示。
- 遇到拒绝的正确操作：**重新打开工程**后重试。你未提交的改动在拒绝时
  已回滚（包括已放置的载荷文件；共享内容库 blob 除外——它按引用计数
  管理，不会被误删）。

## 5. 损坏与不可读

按序自动处理，每一级都先保全证据再恢复：

1. **目录库损坏**（例如磁盘故障写坏 sqlite）：损坏文件被改名保留为
   `*.corrupt-<时间戳>` 以便取证，然后从最近的检查点 `catalog.json`
   重建；重建出的库与检查点一致。
2. **检查点损坏/短写**（例如断电打断检查点写入）：先尝试 `.bak` 备份；
   两者都不可用时报错（附原始路径），不会用空目录覆盖。
3. **暂时不可读**（文件被占用/权限问题）：直接拒绝打开并提示，**不会**
   用检查点覆盖权威库——避免把他人较新的提交滚回旧状态。
4. **只读介质**：库与检查点都无法落盘时拒绝打开（无假成功）；此时请把
   工程复制到可写位置再打开。

## 6. 工程身份

工程路径、工程 id 与名称在打开期间随每个变更事件与恢复报告携带；关闭
重开后工程身份保持不变。数据目录本身不保存 `.paleo.json` 的内容——
工程身份由工程文件层注入，二者互不覆盖。
